# 紧迫交付的小型全栈项目操作手册

适用条件：大技术栈已定，细节可委托，你对具体框架、数据库工具和部署平台都陌生。目标是在截止前交付可运行、核心需求正确、可复验的版本。默认一个主 Agent，负责短设计、实现、测试和交接。你负责范围、业务规则、风险取舍和交付决定。

## 1. 开工前填写交付卡

复制以下内容，先填你知道的。要求 Agent 一次性汇总会影响交付的空项，其他空项按可逆默认值处理。

- 截止时间和时区：____。我能介入的时间窗口：____。
- 交付物：本地可运行 / 指定环境可访问 / 仓库与演示。实际要求：____。
- 固定技术栈、指定版本和部署平台：____。版本未指定时，由 Agent 选互相兼容的版本并记录。
- 必交付流程，按优先级排列：____。每条写成「谁在什么前提下做什么，应看到什么结果」。
- 不能出错的规则：____。明确非法输入、失败是否可重试、重复操作会不会产生额外记录、谁能操作谁的数据，只填写与项目有关的项。
- 截止前可放弃的内容，按砍掉顺序排列：____。首版可接受的限制：____。
- 授权范围：指定仓库、分支、本地/测试环境、可用测试账号和样例数据。生产或真实数据动作逐项标记授权。
- 交付对象和演示账号/测试数据的提供方式：____。凭据通过环境配置提供，提交中只放配置示例。

**你的动作**：提供仓库和必要访问权限，确认真实截止时间及交付形式。若要求部署，开工即确认目标环境入口、账号权限和可用测试数据库。把任何需要别人提供的权限、账号或信息在首个 commit 前解决。

## 2. 首个 commit 前完成准备

本次开发窗口从工作分支的**首个任务 commit 成功**开始，到**最后一个任务 commit 成功**为止，墙钟上限 45 分钟。空提交、重开会话、切换 Agent、等待回复或命令都不重置计时。开工前可做需求澄清、短设计、环境准备与可抛弃的技术实验。正式功能代码从计时开始实现。已有仓库的历史提交不计入本次窗口。

1. **你确认范围。** 列出必须通过的核心验收，以及预先授权的简化方案。每个简化方案写清触发条件和保留的业务结果。可选项默认排除在本次窗口之外。
2. **主 Agent 提交一页短设计。** 写清最短端到端路径、关键约束、计划提交顺序、预计每段耗时、最贵的验证命令与备选路线。已有惯例或常规实现能满足验收时，直接采用。
3. **主 Agent 检查环境，你补齐访问条件。** 开工前确认分支和工作区可用、依赖可安装、测试库可达、验证命令可执行。必须使用目标部署环境时，提前验证其访问、凭据和运行方式。陌生机制只验证足以改变路线的假设。
4. **你确认能否开工。** 按实际测得的环境和验证耗时，确认首条链路能在 15 分钟内完成、剩余核心功能能在第 28 分钟前完成，且验证与提交能放进后续窗口。若缺必要权限、关键假设悬而未决、单次必要检查耗时超出预算，或核心范围预估放不进窗口，先处理阻塞或明确改范围，再创建首个 commit。
5. **主 Agent 创建首个任务 commit。** 使用交付卡、现有基线记录或已确认的启动说明等最小可追踪变更。命令成功后立即记录 T0、绝对截止时间、阶段闸门和 commit ID。准备阶段的草稿或实验与正式实现分开。

## 3. 45 分钟硬预算

| 墙钟 | 到点必须执行 | 你的动作 |
|---|---|---|
| T+0 | 记录时间，按最短路径开工 | 保持可联系，接受已约定的简化规则 |
| T+10 | 检查真实写入与读回是否已有证据。若仍无关键进展，立即启用预授权备选，或发出阻塞信号 | 只回答阻塞核心行为的问题 |
| T+15 | 首条核心链路应已通过并形成可回退提交。未达标时停止开启其余功能，按已授权简化保住核心链路 | 需要改变必交付范围时，当场决定 |
| T+23 | 逐条核对剩余核心验收。预计任何一项无法在 T+28 前完成，立即触发取舍 | 确认可交付范围，或记录该项仍有缺口 |
| T+28 | **冻结功能。** 从此只跑验收、修复阻断项、整理提交。暂停正在做的非验收必需改动 | 检查首要用户流程和关键反例 |
| T+36 | 选定候选。只允许能在 T+40 前修完并复验的阻断修复，超预算则保留最近的已验证提交 | 核对实际通过项和已知缺口 |
| T+40 | **停止修改实现。** 检查最终 diff、暂存区及 commit，留出命令或钩子失败的处理时间 | 核对版本及验收状态 |
| T+43 | 最终提交目标。若新提交未成功，保护最近的已验证提交并按实际状态交接 | 接收 commit ID 和实际状态 |
| T+45 | **硬停止。** 不再启动、重试或等待本窗口内的提交操作 | 依据已成功的提交验收 |

### Agent 的自主计时与停手规则

- 在每次开始分析、开新任务、调用命令、完成阶段、恢复会话时读取真实时钟。每次读取后计算下一道闸门剩余时间。记住 T0 和绝对截止时间，跨会话沿用。
- 每项工作开做前写出「对应哪条验收 / 要产出什么证据 / 最迟何时停」。没有对应的核心验收或发布前置条件，立即跳过。
- **准入计算**：预计耗时加验证时间必须落在该阶段剩余时间内。跨阶段检查须事先排程，不能借用最终提交缓冲。命令使用工具支持的超时或可取消执行，超时上限取该任务预算与距离闸门的较小值。无法可靠限时的命令先在准备阶段验证。工具可设外部截止或取消时启用它，避免单次调用跨越硬停止。
- **过度思考**：连续 2 分钟没有新证据或决策、同一个问题已看两处资料仍在扩大搜索、或已有可行路线还在比较可逆细节。停止搜集，按已验证的最简单路线推进。只有结果能改变核心验收才开限时实验。
- **过度开发**：改动不对应核心验收、开始做抽象或美化、重复实现框架已有能力、扩大文件改动范围、引入没有必要的依赖。立即停止该项，隔离未验证改动，回到当前核心路径。
- **超时预警**：剩余实现加验证预计撞上闸门、一次排错达到 3 分钟或两种尝试无新证据、关键命令超出其预算。立刻终止该方向，采用已授权的简化方案。若仍无法满足核心验收，报告受影响项目和最近可用提交。等待回复期间继续已授权工作，闸门照常生效。
- **保住可交付版本**：每条核心链路通过后保存可回退提交，记下 commit ID 和验证结果。失败中的修改保持隔离。候选只依据实际验证；首版未完成就逐条标为缺失或未验证。
- 这些规则保证窗口和缓冲受到约束。能否完成所有核心需求取决于开工范围、环境及实际故障；未达到验收时按实际结果交付，禁止借时或把缺项标为完成。

### 可直接发给主 Agent 的指令

> 用一个主会话完成。先按开工门槛给出短设计、验收清单和预授权简化路线，确认后创建首个任务 commit。记录 T0，按上表执行。每次调用前检查时钟、验收关联和任务预算。触发过度思考、过度开发或超时信号时自己停止当前方向，先走授权内的备选。随实现维护 README、demo data、startup check、AI export index 和 completeness declaration，T+36 前完成验证与收齐记录。T+28 冻结功能，T+40 停止修改实现，T+43 目标完成最终提交，T+45 硬停止。只在必须由我决定的事项上发升级消息，带上剩余时间、默认动作与最近验证通过的 commit ID。每条核心链路通过后立即保留可回退提交。

## 4. 按可验收的流程推进

| 检查点 | Agent 做什么 | 你做什么 |
|---|---|---|
| 第一条真实链路 | 在浏览器完成一个核心动作，经服务端写入真实测试库，刷新或重新查询验证结果。提供启动命令、测试账号和演示步骤 | 亲自走一遍。核对实际结果与业务规则。若结果有误，写清「输入、预期、实际」让 Agent 修正 |
| 后续切片 | 每次完成一个可验收行为。先确认正常和关键失败用例，再实现、验证并形成可回退的提交 | 只在检查点看结果。常规决定由 Agent 自行处理。按优先级决定哪些问题立即修 |
| 风险变更 | 给出关键代码位置、测试和复现。权限检查覆盖直接调接口，持久化检查数据库实际状态，迁移按需要覆盖已有数据 | 对权限、关键数据约束、事务或迁移，亲自核对机制及反例。看不懂陌生机制时要求最小复现和版本文档 |
| 冻结前 | 把必交付项逐条标记通过、失败或未验证，列出影响及剩余时间 | 按表决定继续、砍可选项或修改交付承诺。冻结后暂停功能新增 |

每个切片要求 Agent 汇报四项：已交付行为、实际执行的检查及结果、未验证项、下一步与预计风险。对进度使用检查点汇报。出现下表的升级信号就立即汇报。

**第二个 Agent 的启动条件**：有一个具体且值得独立核实的问题，同时能并行并在当前阶段闸门前给出证据。给它原始规则、变更和复现环境，让它只审指定问题，允许在隔离环境运行检查。它交付触发条件、代码位置和复现结果。主 Agent 统一修复，你根据风险决定合并。若只剩很少时间，由你和主 Agent 直接验证最高风险反例。普通技术选型和例行审查留在主会话。

## 5. 介入信号与响应

| 信号 | Agent 停在哪里 | 你的下一步 |
|---|---|---|
| 两种解释会改变核心行为、数据结果或验收 | 暂停相关实现，列具体输入及两种预期 | 选一条规则，给一个验收例子 |
| 需要删减必交付流程，或预计侵占交付缓冲 | 停止可选工作，报告剩余量、预计完成时间和可交付子集 | 先砍已授权的可选项。必交付范围变化由你决定并更新交付卡 |
| 要换指定大技术栈、改变公共接口、核心模型或权限边界 | 暂停越界改动，列影响和最小可行路线 | 决定保留现状、接受改变或调整范围 |
| 新依赖引入外部服务、持续费用、额外权限或数据传输 | 暂停接入，给出成本、数据去向及可行替代 | 明确授权、选替代或缩小范围 |
| 缺凭据、账号权限或外部配置 | 报告缺项和所需最小权限，继续本地工作 | 提供安全的访问方式，或明确改交付环境 |
| 发现秘密泄露、越权、数据损坏或疑似访问错误环境 | 停止相关操作，保留经过脱敏的证据 | 核实影响，决定隔离、轮换、恢复或修复，再恢复工作 |
| 将执行未授权的发布、生产迁移、真实数据写入或不可逆操作 | 停在命令执行前，给出目标、影响、验证及恢复方案 | 核对目标环境，明确批准该动作或要求先演练 |
| 与你的工作区改动冲突，或需要覆盖历史、删除重要内容 | 保留现场，暂停冲突文件的改动 | 指定保留内容或隔离分支 |
| 核心测试失败、真实集成无法验证，或只有降低标准才能继续 | 保留失败输出，标记未验证，报告备选 | 决定修复、恢复到可用版本、改范围或延期 |
| 阻塞实验到时间上限，或两种不同尝试都没有新证据 | 停止重复尝试，提交最小复现和已排除项 | 选已验证备选、投入额外时间，或调整交付 |
| 最终合并、正式发布或对外宣称验收完成 | 提交候选版本和验证记录 | 按发布清单验收并作决定 |

Agent 的升级消息统一写成：「需决定的事项 / 已有证据 / 选项与推荐 / 最晚决策时间 / 等待期间能继续的工作」。没有收到决定时，按已授权的范围推进；受阻路径保留现状。局部组件、命名、目录、可逆实现细节和常规排错可直接处理。用户暂时离线时，Agent 仍可提交候选版本、验证结果和交接材料。

## 6. 验收、发布和交接

### Agent 在交付候选上执行

- 记录提交或构建版本。从干净检出按文档安装依赖、配置、启动，对空测试库跑迁移和初始化。版本或环境变化后复验相关路径。
- 跑构建和项目已有检查。针对必交付项跑核心成功流程和关键反例。真实数据库验证写入、读回和必要的失败后状态。适用时验证非法输入、未登录或越权、重复操作、已有数据迁移。
- 部署是交付项时，在实际目标环境验证入口、核心流程、日志和数据库连接。部署与迁移顺序、恢复路径和授权记录明确。实际失败时按预案停住或恢复到已验证版本。
- 交付 README 或等价说明，包含依赖版本、配置变量名、启动/迁移/测试命令、演示步骤、核心代码入口、日志位置及已知限制。命令使用实际跑过的版本。
- 给出一张验收表，每行包含需求、验证方式、实际结果、环境与版本。未执行写「未验证」，有失败给复现步骤。

### 你在截止前执行

1. 核对候选版本与验收表一致，至少亲自走首要用户流程。需要目标环境交付时，从交付对象可用的入口操作一次。
2. 检查最重要的失败场景和对应证据。例如验证越权请求被拒后，相关数据也没有改变。按风险复查数据约束和迁移。
3. 确认可选缺项已记录，必交付失败项已处理或已明确改变交付承诺。
4. 批准或执行授权范围内的合并和发布。发布后核对实际版本并跑一次冒烟测试。发现阻塞故障，执行已确认的恢复方案并记录实际状态。
5. 交接入口、版本、复现步骤、已知限制和接下来需要处理的事项。

### 计时范围和交接

提交窗口内完成与候选 commit 对应的核心验证。部署若是验收项，开工前明确是窗口内的必要验证，还是最终提交后的发布动作，并为其单独留出时间。最终提交后可以发送交接和执行已授权的发布，不再补代码或创建本窗口内的提交。交接至少给出最终 commit ID、首末提交时间、通过项、未通过或未验证项。


## 7. 五项强制交付物与完成标准

五项均进入交付卡和时间预算。Agent 在开工前确认模板、目录和 AI 记录导出方式，随实现维护。T+28 核对五项齐备，T+36 前完成启动验证、数据复验与声明更新，T+40 前锁定内容，随最终代码一起提交。缺任一项即报告交付缺口。外部导出文件可按约定交付到独立目录，仓库中提交其索引。

| 交付物 | 最小内容与验收动作 | 产出时点 |
|---|---|---|
| README.md | 固定版本、环境变量示例、安装、建库/迁移、导入演示数据、启动、验证、停止命令，入口地址和核心演示步骤。每条命令按新使用者的顺序列出，实际跑过后标明结果。你按 README 操作首要流程 | 首条链路完成时同步写入，后续随变更更新 |
| Demo data | 提交种子脚本或数据文件及导入命令，覆盖核心演示和必要边界场景，使用虚构数据。说明测试账号、预期记录及重复执行策略。Agent 在隔离测试库验证可重复导入且结果符合声明。清空数据仅限已授权的测试库 | 首条链路使用该数据，T+28 前齐备 |
| Startup check | 提交可一键执行的脚本，或沿用已有启动检查命令。检查配置存在、数据库可达、必要表可用、服务就绪，以及一条最小前后端到数据库的路径。设总超时、失败返回非零并指出失败步骤，写入测试数据时使用隔离记录。复用首条链路的验证，记录命令、环境、时间与结果 | 首条链路即有可复用检查，T+36 前在候选上复验 |
| AI export index | 默认路径 docs/ai-export-index.md。每条记录含工具/会话标识、时间范围、导出文件路径或可访问链接、覆盖的任务及关联代码阶段。开工前试验一次导出。T+28 导出已完成部分，T+36 前检查可打开且路径有效，末段导出覆盖到最后一次代码修改。若工具仅支持手动导出，Agent 提前提示你执行。工具没有原生导出时，在开工前由你认可已有可审计记录的替代方式 | 首个 commit 前确认能力与操作，过程持续记录，T+40 前收齐 |
| Completeness declaration | 默认路径 COMPLETENESS.md。逐条列出原始核心需求及五项交付物，标记完成并验证 / 已实现未验证 / 缺失，附证据路径和限制。记录验收环境、实现版本和首个提交时间。验收你明确接受的范围，并保留原始要求与变更记录 | 从交付卡生成，T+28 开始逐项关账，T+40 前更新完成 |

**版本关联**：声明和日志指向实际验证过的实现 commit，声明所在的最终提交可另在交接消息给出完整 ID 与提交时间。最后一次仅修改交付文档时说明这一点；若实现变了，复验受影响项。避免为把最终提交自己的哈希写进文件而产生无限补交。

**导出边界**：AI export index 按 AI 会话/工具记录导出的索引解释。记录实际覆盖到的时间与阶段；末段仅有提交和交接时，注明导出截止点及此后动作。工具记录缺失、导出权限不足或评审方要求完整原始导出时，在开工前解决。人工摘要只能在你认可的情况下作为替代，并明确标记来源。

**你需要介入的新增信号**：导出必须手动操作或缺少权限、演示数据涉及真实信息、启动检查要求操作未授权环境、五项交付物任一项预计无法在 T+40 前完成。Agent 报告具体缺项、最晚动作时间和默认处理。你在开工前确认导出形式与验收要求；窗口内按提示执行必要的手动导出。在最终检查时打开索引里的文件，按 README 跑演示，并核对完整性声明中的缺项。

**控制工作量**：README 直接记录实际命令，演示数据直接用于核心验收，启动检查复用已有脚本，完整性声明直接维护需求表，AI 索引只写定位信息。模板和格式一次确定，后续只更新事实。

## 依据与适用边界

小批量交付依据 [DORA 的小批量工作实践](https://dora.dev/capabilities/working-in-small-batches/)。按任务依赖决定是否并行参考 [Google Research 的 Agent 配置实验](https://www.research.google/blog/towards-a-science-of-scaling-agent-systems-when-and-why-agent-systems-work/)。陌生机制用解释与复现建立理解参考 [Anthropic 的陌生编程库随机实验](https://www.anthropic.com/research/AI-assistance-coding-skills)。45 分钟阶段闸门与判停阈值、单主 Agent、介入门槛及冻结策略是针对本手册约束的执行默认值。
